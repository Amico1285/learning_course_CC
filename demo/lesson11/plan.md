## Детальный разбор

### Playwright

Сценарии применения:

- **Feedback loop при разработке прототипов.** Агент правит фронтенд, открывает страницу, видит результат, итерирует.
- **Автоматизация поиска, когда у модели нет доступа через стандартный `fetch`** -- например, сайт за Cloudflare, требует JS, или нужны динамические данные.
- **Сценарий с авторизацией.** Пользователь просит агента открыть вкладку через Playwright, сам логинится в этой вкладке, после чего агент продолжает работу в уже залогиненной сессии.

#### Альтернативы и когда что использовать

- **Puppeteer MCP.** Раньше использовал его. Сейчас переведён в архив, потребляет заметно больше токенов и работает хуже Playwright -- не рекомендую.
- **Плагин Claude от Anthropic для Chrome.** Управляет вкладкой прямо из браузера. У меня стоит, периодически пользуюсь -- но только когда задаче не нужен контекст проекта. Например, надо заполнить форму, и я понимаю, что за минуту объясню модели, что делать; знание не связано с кодовой базой. Тогда удобно как независимый инстанс.
  - Развилка: **Playwright из проекта** -- когда модели нужен широкий контекст репозитория. **Плагин в Chrome** -- когда контекст не нужен, разовое действие на странице.
- **Claude Code с флагом Chrome.** У Claude Code есть режим со встроенным MCP-сервером для управления Chrome. Минус -- он подключается к вашему личному Chrome (закладки, возможно пароли), на каждое действие нужно выдавать разрешение. Мне показалось неудобно, практически не использую.

#### Установка в Claude Code

Ставится через плагин на уровне юзера -- настраивать что-либо в проекте не нужно.

#### Несколько изолированных копий для параллельной работы

Один MCP-сервер Playwright -- одно состояние браузера. Если в проекте несколько агентов одновременно работают с Playwright, они конфликтуют: один перебивает вкладку другого.

Решение -- в самом проекте объявить несколько именованных серверов в `.mcp.json`. Каждый агент берёт свой:

```json
{
  "mcpServers": {
    "pw-1": { "command": "npx", "args": ["@playwright/mcp@latest", "--isolated"] },
    "pw-2": { "command": "npx", "args": ["@playwright/mcp@latest", "--isolated"] },
    "pw-3": { "command": "npx", "args": ["@playwright/mcp@latest", "--isolated"] },
    "pw-4": { "command": "npx", "args": ["@playwright/mcp@latest", "--isolated"] },
    "pw-5": { "command": "npx", "args": ["@playwright/mcp@latest", "--isolated"] }
  }
}
```

Флаг `--isolated` запускает каждый сервер с собственным временным профилем браузера, поэтому параллельные запуски не блокируют друг друга.

### Kaiten MCP

Kaiten -- система управления задачами (как Jira или Trello). MCP-сервер позволяет агенту работать с задачами в Kaiten напрямую: создавать карточки, двигать по колонкам, оставлять комментарии, логировать время -- всё через текстовые команды. 63 инструмента: карточки, комментарии, чеклисты, теги, учёт времени, блокеры, внешние ссылки, файлы и др.

Написан автором курса. Установка, конфиг и сценарии использования -- в [уроке 8](../lesson8/plan.md).

#### Что это даёт против ручного ведения

1. **Скорость рутины.** Создавать карточки голосом, вешать чеклисты, ставить блокеры -- то, что в UI требует много кликов, через агента укладывается в одну реплику.

2. **Bulk-операции.** Массовые перемещения, проставление тегов, создание серии однотипных карточек. В UI почти отсутствуют; через агента -- одна команда вместо 50-100 кликов.

3. **Учёт времени без боли.** "Залогируй 1.5 ч на карточку #1234 за вчера" -- 5 секунд против 30 кликов. Дисциплина учёта растёт там, где сама не растёт.

4. **Соблюдение формата ведения.** У команды есть формат описания задач (структура, теги, обязательные поля). Описать его в промпте -- и модель будет следить за паттерном аккуратнее, чем человек, который "помнит, как надо".

5. **Visibility поверх доски.** Модель пробегает по карточкам, смотрит свежие изменения и подсвечивает, на что обратить внимание: "появилось 3 новых блокера за сутки", "карточка #X в Review шестой день".

6. **Поиск застрявшего через `location_history`.** В Kaiten хранится, сколько карточка просидела в каждой колонке. Запрос "найди карточки, которые висят в Review дольше 5 дней" показывает, **где процесс затыкается** -- в UI этого не видно.

7. **Аналитика на лету без выгрузок.** "Сколько часов команда залогировала на эпик X в марте", "топ-5 карточек по затраченному времени", "кто сколько закрыл задач". Раньше -- задача аналитика; теперь -- 30 секунд.

8. **Подготовка к встречам.** Стендап, 1:1, ретро. "Собери, что я делал на этой неделе: какие карточки двигал, где логировал время, что застряло" -- продакт приходит с готовой сводкой. На ретро: "найди карточки, которые гуляли между колонками больше 5 раз" -- симптом плохого процесса.

9. **External links и интеграция с другими системами.** Привязать карточку к GitHub-issue, PR, Figma-ссылке без копипасты URL и переключения вкладок: "привяжи к карточке #1234 этот PR и оставь комментарий, что готово к ревью".

10. **Низкий порог входа для новых членов команды.** Не нужно учить интерфейс Kaiten. "Покажи активные карточки команды", "найди похожие задачи в прошлом" -- агент работает как оверлей знаний над доской.

11. **Прозрачность процессов и стыковка с AI-агентами.** Раньше многие вещи не вносились в задачи -- муторно для отдачи. Теперь окупается: модель в 10 раз быстрее. Прозрачность растёт; меньше держится на устных договорённостях, больше -- через трекинг. И это же делает процесс пригодным для встраивания других AI-агентов: им есть откуда читать состояние и куда писать апдейты.

#### Две оси ценности

Список выше распадается на две разные истории:

- **Скорость** -- то же, что делалось руками, но быстрее: создание карточек, учёт времени, перемещения, проставление тегов. Те же действия, экономия времени.
- **Новые возможности** -- то, что **раньше не делали**, потому что не окупалось: регулярная аналитика, аудит застрявшего, подготовка сводок к встречам, очистка backlog. Меняется не "как делать", а "что вообще делать".

Вторая ось интереснее: она про новые рутины, которых до агента в команде просто не существовало.

### MCP для векторного поиска

`mcp-vector-search` (автор курса). Семантический поиск по локальной коллекции файлов -- документации, ресерчам, наработкам. Файлы кладутся в векторную БД, агент ищет "по смыслу", а не по литералу.

Что умеет:

- Семантический поиск по embeddings -- VoyageAI / OpenAI (cloud) или Ollama (локально).
- BM25 -- поиск по ключевым словам (точные фразы, имена, error strings).
- Гибрид: BM25 + семантика через Reciprocal Rank Fusion -- когда нужны и точные совпадения, и смысл.
- Фильтрация по папкам -- можно искать только в `competitors/cyberark/`, например.

#### Что это даёт против Grep / Glob

- **Семантика.** Grep пропустит, если термин в документации назван иначе ("just-in-time elevation" vs "временное повышение прав"). Векторный поиск найдёт по смыслу.
- **Объём.** Документация одного продукта (например, CyberArk Privilege Access Management) -- больше 10 МБ. Grep по такому объёму, не зная структуры документации вендора, выдаёт сотни ложных совпадений. Векторный поиск возвращает 5-10 наиболее релевантных кусков.
- **Адаптивная отдача.** Обычный векторный поиск всегда возвращает K результатов независимо от релевантности. Здесь стоит reranker с порогом: если ничего не подходит -- возвращает **ноль**. Это сохраняет контекст агента и снижает шанс, что вывод построится на нерелевантных кусках.

#### VoyageAI -- лучший семантический поиск бесплатно

VoyageAI -- сильнейший провайдер embeddings и reranker'а на сегодня. По регистрации даёт большой пул бесплатных токенов; для бытового ресерча лимита хватает с запасом. Для приватных корпусов (внутренние документы компании) -- Ollama локально, без внешних запросов.

#### Главный юзкейс: feature parity analysis конкурентов

Сценарий, который до векторного поиска по докам сделать было практически нереально:

1. Через Playwright (см. урок 10) скрапим документацию 10 конкурентов в локальные папки: `competitors/cyberark/`, `competitors/beyondtrust/`, и т.д.
2. Векторизуем всё в одну базу.
3. Запускаем **10 агентов параллельно** -- каждому узкая задача в своей папке: "Найди в `competitors/<vendor>/`, как реализован Just-in-time access".
4. Главный агент сводит ответы в таблицу `vendor × фича × краткое описание`.

Почему этого нельзя достичь обычным ресерчем в интернете:

- Реальные продукты никто не даст просто так поставить и разобраться -- недели сетапа на каждый.
- Документация -- лучшее **зеркало** реального продукта: если фича есть, она там описана; если нет -- её нет.
- Семантический поиск по докам открывает аналитическую работу, которая раньше была за пределами разумного бюджета времени: можно сравнивать 10 продуктов по десятку фич за один вечер вместо квартала ручного ресерча.
